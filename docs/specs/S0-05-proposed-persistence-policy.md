# S0-05 — Proposed Persistence and Identity Policy

**Status:** PROPOSED. A proposal that depends on the answers in the
[Owner Decision Register](S0-05-owner-decision-register.md). **Nothing here is implemented or approved.** The SQL below is an
illustrative sketch of what the recommended choices would imply; it is not a migration.

**Principle:** no implicit uniqueness and no implicit normalisation. Every constraint that will exist is listed in section 9,
and every constraint that will deliberately **not** exist is listed next to it.

## 1. Internal UUIDv7 identity

- **Policy:** UUT, TestAttempt and InvestigationCase each have an internal identifier generated by the Shared Kernel
  (`EntityId<'UUT'>`, `EntityId<'TestAttempt'>`, `EntityId<'InvestigationCase'>`), stored as PostgreSQL `uuid`, validated as
  UUIDv7 on the way in and out of the domain. The database does not generate identifiers.
- **Link identity:** an association identified by its natural key `(case, attempt, role)` unless the Owner chooses its own
  UUIDv7 (Register Q6, additional consideration).
- **Not done:** no identity is derived from SN, hostname, execution identity or any external value.
- **Depends on:** Q2, Q6.

## 2. External SN and hostname

- **Policy (recommended Q3-A):** optional text attributes of the UUT, stored exactly as given. No trimming, no case folding, no
  uniqueness, no check constraint. They are never used as a key and never treated as authoritative identity.
- **Not done:** no "find or create UUT by serial number", because that would silently treat an external identifier as
  identity. Ambiguous identity (two UUTs with the same SN) is representable and is a reconciliation concern outside S0-05.

## 3. Test stage and execution identity

- **Policy (recommended Q4-A, U1, R1):** both are required (non-null) free-text attributes of the TestAttempt, stored as
  given. No enumeration, no uniqueness, no result field.
- **Not done:** no inference of a test outcome, no uniqueness of the execution identity, no vocabulary for the stage.

## 4. Link uniqueness and role multiplicity

- **Policy (recommended Q5-K1, D1, M1):**
  - the link key is `(case_id, attempt_id, role)`;
  - role is one of `INITIAL_FAILURE`, `RETEST`, `SUPPORTING`, `CONTEXT` (the roles the specification lists);
  - repeating an identical link is an idempotent no-op that returns the existing link and does not advance the case version;
  - linking the same attempt again with a different role creates a second link (the key differs);
  - no limit on the number of links per role, and roles are immutable: changing a role means creating another link.
- **Not done:** no "exactly one INITIAL_FAILURE" rule and no automatic closing of a case. Linking a RETEST records the
  relationship only; it establishes no repair effectiveness and no RCA conclusion.

## 5. Same-UUT protection

Enforced twice, by the same mechanism that already protects observations in `0002`:

- **Application:** the domain operation that links an attempt to a case compares the two UUT references and refuses a
  mismatch without attaching anything.
- **Database:** `investigation_case` and `test_attempt` each have `unique (id, uut_id)`. The link row stores one `uut_id` and
  has two composite foreign keys, `(case_id, uut_id)` to the case and `(attempt_id, uut_id)` to the attempt, so a row whose two
  sides name different UUTs cannot exist.
- **Existing evidence:** `apps/api/src/composition/investigation.integration.test.ts` already proves this mechanism for
  observations (domain rejection, and a raw SQL insert rejected with SQLSTATE 23503).

## 6. Optimistic concurrency

- **Policy (recommended Q6-A):** only `investigation_case` is versioned. A mutating operation (linking) is saved with
  `update ... set version = version + 1 where id = $1 and version = $2 returning version`; zero rows is a conflict, never a
  silent overwrite. UUT and TestAttempt are immutable after creation and carry no version.
- **Stale versus missing:** the repository distinguishes a stale version from a missing case by checking existence inside the
  same transaction, so callers see `case_not_found` or `concurrency_conflict` and never a silent success.
- **Transactions:** unchanged. The application owns the `TransactionScope`; the case update, the new link rows and the error
  paths commit or roll back together.
- **If the Owner chooses Q6-B:** nothing is versioned and optimistic concurrency cannot be demonstrated on a real record,
  which acceptance criterion 6 requires; this is recorded as a consequence of that option.

## 7. Deterministic query ordering

- **Policy (recommended Q9-O1):** linked attempts are returned ordered by attempt id ascending (UUIDv7, so registration
  order), then by role in the order `INITIAL_FAILURE`, `RETEST`, `SUPPORTING`, `CONTEXT`. Every list query has an explicit
  `ORDER BY`; no caller depends on insertion or heap order.
- **Not done:** no ordering by a timestamp column (none is proposed, Q10-T1).

## 8. Illustrative sketch (not a migration)

```sql
create table investigation.uut (
  id            uuid primary key,
  serial_number text,                 -- optional, stored as given, not unique
  hostname      text                  -- optional, stored as given, not unique
);

create table investigation.test_attempt (
  id                 uuid primary key,
  uut_id             uuid not null references investigation.uut (id),
  stage              text not null,   -- free text, stored as given
  execution_identity text not null,   -- free text, stored as given, not unique
  constraint test_attempt_id_uut_key unique (id, uut_id)
);

create table investigation.investigation_case (
  id      uuid primary key,
  uut_id  uuid not null references investigation.uut (id),
  version integer not null default 1 check (version >= 1),
  constraint investigation_case_id_uut_key unique (id, uut_id)
);

create table investigation.case_test_attempt_link (
  case_id    uuid not null,
  attempt_id uuid not null,
  uut_id     uuid not null,
  role       text not null check (role in ('INITIAL_FAILURE', 'RETEST', 'SUPPORTING', 'CONTEXT')),
  primary key (case_id, attempt_id, role),
  foreign key (case_id, uut_id)    references investigation.investigation_case (id, uut_id),
  foreign key (attempt_id, uut_id) references investigation.test_attempt (id, uut_id)
);
```

## 9. Constraints that will and will not exist

| Constraint                                             | Exists          | Why                                                           |
| ------------------------------------------------------ | --------------- | ------------------------------------------------------------- |
| Primary keys on the three entities and on the link key | yes             | Identity (UUIDv7) and the link key (Q5)                       |
| `unique (id, uut_id)` on case and attempt              | yes             | Supports the same-UUT foreign keys                            |
| Composite foreign keys on the link                     | yes             | Same-UUT protection at database level                         |
| Foreign keys from case and attempt to `uut`            | yes (Q2-A or C) | Existence of the UUT inside the context                       |
| `check (role in (...))`                                | yes             | The four roles are listed by the specification                |
| `check (version >= 1)` on the case                     | yes             | Optimistic concurrency                                        |
| Uniqueness of serial number or hostname                | **no**          | Specification forbids treating them as authoritative identity |
| Uniqueness of execution identity                       | **no**          | Not specified                                                 |
| Limit on links per role                                | **no**          | Not specified                                                 |
| Any `check` on the content of text attributes          | **no**          | No limits, trimming or normalisation may be invented          |
| Timestamp columns                                      | **no** (Q10-T1) | Not specified                                                 |
| Status or lifecycle columns                            | **no**          | Section 3 forbids a lifecycle state machine in this task      |

## 10. Migration policy (needs a decision with the register)

Migration `0002` is unreleased: it is not merged and not applied to any shared environment, but it has been applied to
developer databases. Two options:

- **M-edit.** Rewrite `0002` into the final shape. Developers run `pnpm db:reset`; `pnpm db:status` reports `modified`
  otherwise. The history stays small. This is what was done when the unapproved description rules were removed.
- **M-forward.** Keep `0002` untouched and add `0003` that drops `failure_observation` and `opened_at` and creates the new
  tables. History is append-only and nothing is edited, at the price of a migration that undoes part of the previous one.

**Recommendation:** M-edit while nothing has been merged, and M-forward from the first merge on. Checksums of `0001` do not
change either way.
